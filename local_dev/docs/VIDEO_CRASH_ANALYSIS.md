# AVAT 영상 디코더 종료 로그 분석

제공된 로그와 `main.py → investigator.app → MainWindow` 실행 경로를 기준으로 분석했다. 문제 영상, 장애 환경의 라이브러리 버전, 프로세스 덤프가 없어 정확한 재현 조건과 최초 원인은 확정할 수 없다. 최초 분석 이후 반복 탐색에 대한 완화 조치를 추가했다.

## 재생바 반복 조작과의 관련성 및 반영한 조치

빠른 반복 조작은 **오류가 드러나는 계기**가 될 수 있다. 이전 구현에서는 드래그 중 이동할 때마다 `CAP_PROP_POS_FRAMES` 설정과 디코딩을 반복했다. FFmpeg의 프레임 스레드 flush는 내부 잠금과 작업 스레드 정리를 사용하므로 빈번한 랜덤 탐색이 해당 경로의 결함이나 비정상 영상 처리를 반복해서 자극할 수 있다. 다만 현재 앱에서는 캡처 호출이 메인 스레드에서 직렬 실행되므로, 드래그가 곧 Python 코드의 동시 디코딩을 뜻하지 않는다. 로그만으로 반복 조작이 최초 원인이라고 확정할 수 없다. [FFmpeg flush와 잠금 코드](https://www.ffmpeg.org/doxygen/7.1/pthread__frame_8c_source.html)

- 드래그 요청을 75ms 간격으로 묶는 방식을 시험했으나 조작 지연이 느껴진다는 피드백에 따라 제거했다. 현재는 기존처럼 드래그 위치마다 즉시 탐색하며, 타이머 대기나 지연 요청을 남기지 않는다.
- 영상 읽기는 기존의 `cv2.VideoCapture(path)`를 사용하며 백엔드와 스레드는 OpenCV의 자동 설정을 따른다.
- 일시정지 상태에서 드래그할 때 오디오 플레이어에는 매번 탐색을 요청하지 않는다. 최종 위치만 기록하고 재생할 때 한 번 적용한다. 오디오 출력을 추가하면서 생긴 불필요한 반복 작업을 줄인다.
- 이미 표시 중인 프레임으로의 탐색은 다시 디코딩하지 않는다. 탐색 실패 시 재생과 소리를 일시정지한다.
- 실제 MJPEG/PCM 시험 영상에서 소리 디코딩·출력 연결·일시정지·탐색·재개를 검증했고, 무음 영상에서 150회 랜덤 탐색을 검증했다. 원래 장애 H.264 영상과 다른 환경의 재현 시험을 대체하지는 않는다.

## 로그별 의미

| 로그 | 의미와 판단 |
| --- | --- |
| `left block unavailable for requested intra mode` | H.264 화면 내 예측에 필요한 왼쪽 인접 블록을 사용할 수 없는 상태. FFmpeg는 해당 경로에서 잘못된 데이터 오류를 반환한다. 파일 손상·잘린 스트림·인코딩 비정상·탐색 이후 디코더 상태 문제 등이 후보이며, 이 로그만으로 파일 손상을 확정할 수 없다. |
| `error while decoding MB 0 25` | 매크로블록 좌표 (0, 25)에서 디코딩에 실패했다는 뜻이다. 25번 프레임 또는 25초를 의미하지 않는다. 이 로그만으로 프로그램 강제 종료 원인을 판단할 수 없다. |
| `Assertion fctx->async_lock failed at libavcodec/pthread_frame.c:178` | FFmpeg 프레임 병렬 디코더에서 잠금 해제 시 잠겨 있어야 한다는 내부 조건이 깨진 것이다. 두 번째 로그에서 확인되는 직접적인 종료 지점이며, 일반적인 Python 예외가 아니라 네이티브 assertion이다. |
| `QThreadStorage: entry ... destroyed before end of thread ...` | 스레드가 끝나기 전에 스레드 로컬 저장소가 정리됐다는 Qt 경고다. 종료 순서 문제가 있음을 나타내지만, 제공된 순서에서는 앞선 디코더 종료에 따른 후속 경고일 가능성이 있다. 별도의 원인일 가능성도 배제할 수 없다. |

두 로그 묶음은 서로 다른 종료 사례이므로 첫 번째 디코딩 오류가 두 번째 assertion을 유발했다고 단정하지 않는다.

근거: [FFmpeg H.264 예측 블록 검사](https://ffmpeg.org/doxygen/7.1/h264__parse_8c_source.html), [FFmpeg 프레임 스레드 잠금 코드](https://www.ffmpeg.org/doxygen/7.1/pthread__frame_8c_source.html), [Qt QThreadStorage 수명 관리](https://doc.qt.io/qt-6.8/qthreadstorage.html).

## 최초 분석 당시 코드에서 확인한 사항

- `investigator/video_controller.py`는 기본 `cv2.VideoCapture(path)`를 사용한다. 디코더 스레드 수를 지정하지 않아 백엔드의 기본 병렬 디코딩 설정을 따른다.
- 컨트롤러의 `read`, `set(CAP_PROP_POS_FRAMES)`, `release`는 메인 스레드의 Qt 이벤트 처리 경로에서 호출된다. 현재 코드에서 동일 캡처를 여러 Python 작업 스레드가 동시에 사용하는 경로는 찾지 못했다. FFmpeg 내부 작업 스레드의 동기화 문제까지 배제할 수 있다는 뜻은 아니다.
- 버튼과 단축키 탐색은 일시정지한 뒤 이동하며, 영상 교체·창 닫기에서는 타이머를 정지하고 캡처를 해제한다. 무분별한 동시 접근이나 캡처 해제 누락을 원인으로 확정할 근거가 없다.
- `open_video`, `seek`, 재생 처리의 `try/except`는 Python으로 전달되는 오류를 처리한다. FFmpeg의 assertion에 따른 프로세스 중단은 이 처리로 복구할 수 없다.
- `pyproject.toml`과 `requirements.txt`는 OpenCV 버전을 범위로 지정한다. 다른 PC에서 설치 시점에 따라 다른 OpenCV/내장 FFmpeg 조합이 설치될 수 있다.
- 저장은 작업·완료·종료 등의 저장 동작에서 이뤄진다. 강제 종료 시 마지막 저장 이후 입력은 유실될 수 있다.

## 원인 분리를 위한 확인 순서

1. **문제 영상의 동일성 확인:** 정상 PC와 장애 PC에서 SHA-256을 비교한다. 재생 시간·파일 크기만으로 동일 파일이라고 판단하지 않는다.
2. **영상 자체 디코딩 검사:** 복사본에 대해 `ffmpeg -v error -i "문제영상.mp4" -f null -`를 실행한다. 같은 구간에서 계속 오류가 나면 스트림 자체 문제 가능성이 높다. 검사 도구의 FFmpeg와 OpenCV 내장 FFmpeg가 다를 수 있으므로 결과가 정상이어도 앱 디코더 문제는 배제하지 않는다.
3. **런타임 비교:** 양쪽 환경에서 Python, PySide6/Qt, OpenCV 버전과 `cv2.getBuildInformation()`의 Video I/O/FFmpeg 항목을 수집한다. 설치된 `opencv-python`, `opencv-contrib-python`, headless 변형의 중복 설치도 확인한다.
4. **발생 동작 분리:** 같은 구간을 순차 재생할 때, 앞뒤 탐색할 때, 영상 전환할 때, 창을 닫을 때 중 어떤 동작에서 발생하는지 기록한다. 문제 영상과 정상 영상을 각각 비교한다.
5. **별도 시험에서 단일 스레드 검증:** `cv2.VideoCapture(path, cv2.CAP_FFMPEG, [cv2.CAP_PROP_N_THREADS, 1])`로 열어 assertion 재발 여부와 탐색·재생 성능을 비교한다. 이 속성은 열 때만 적용되고 FFmpeg 백엔드용이다. 캡처를 연 뒤 `set()`으로 적용하는 방식은 적절하지 않다. 단일 스레드는 진단 및 완화 후보이며 손상된 영상을 복구하지 않는다. [OpenCV 속성 정의](https://docs.opencv.org/4.12.0/d4/d15/group__videoio__flags__base.html)

우선순위는 **동일 영상 + 동일 라이브러리 버전으로 재현 → 단일 스레드 비교 → 확인된 조합 고정**이다. 단일 스레드에서도 네이티브 중단이 계속되면 디코더를 별도 프로세스로 분리해 영상 처리 실패가 전체 UI 종료로 이어지는 범위를 줄이는 방안을 검토한다. 재인코딩이 필요하면 원본을 보존하고, 프레임 번호·FPS·마커 대응이 달라지는지 별도 검증해야 한다.
